# Technical-writing style references

Use the current authoritative guides as the source of truth:

- [Google developer documentation style guide](https://developers.google.com/style)
- [Microsoft Writing Style Guide](https://learn.microsoft.com/style-guide/welcome/)

Do not reproduce the guides wholesale. Consult the relevant topic when a wording decision is uncertain or consequential.

## Shared working principles

The guides broadly favor documentation that is:

- Clear, concise, conversational, and useful to the reader.
- Written in active voice and present tense when those constructions are natural.
- Focused on the reader, commonly using **you** for instructions.
- Organized around tasks and easy to scan with descriptive headings and parallel lists.
- Consistent in terminology, capitalization, punctuation, and treatment of UI and code elements.
- Inclusive, accessible, and understandable to an international audience.
- Free of unnecessary jargon, idioms, slang, anthropomorphism, and culture-specific references.

## Review notes

- Prefer short, direct sentences, but do not split sentences so aggressively that relationships between ideas become unclear.
- Use contractions only when they suit the project's voice and do not reduce clarity or localization quality.
- Keep established technical terms and exact interface labels even when ordinary prose would use a different form.
- Use parallel grammatical structures for headings, steps, and list items.
- Make prerequisites, conditions, expected results, cautions, and errors explicit.
- Treat accessibility and inclusive-language changes as substantive reasons, not merely cosmetic preferences.

Repository-specific guidance takes precedence because open-source projects often have established vocabulary, formatting, and contributor expectations. If Google and Microsoft differ on a matter not settled by the project, prefer the option that is clearest and least disruptive, and describe it as a style choice rather than a grammar rule.
